# Comprehensive Audit — gossip monorepo

**Date:** 2026-07-08
**Scope:** `packages/gossip` (all five layers), `packages/gossip_nearby`, `packages/gossip_bluey` — ~16.4k LOC across 120 lib files. Examples read only to establish reachability; not audited.
**Rubrics:** (1) protocol correctness & missing functionality, judged against anti-entropy gossip (Demers et al. 1987), SWIM (Das/Gupta/Motivala 2002), version vectors, and HLC practice; (2) performance at the deployment reality (phones, BLE at a few KB/s, 32 KB frames, n ≤ 8, single isolate shared with the UI); (3) Clean Architecture + DDD compliance, judged against both the canonical rubrics and the repo's own ADR-010.
**Baseline:** [2026-07-06 correctness audit](2026-07-06-correctness-audit.md) and [2026-07-06 algorithm audit](2026-07-06-algorithm-audit.md), both marked fully remediated. Every remediation claim relevant to a finding was re-verified against today's source (branch `working-connection`, HEAD `499a389`).
**Method:** 8 parallel deep-read auditors by territory (protocol / domain / application+facade / infrastructure / gossip_nearby / gossip_bluey / CA+DDD / performance), each reading its territory **in full**. Gates run by the orchestrator: `melos run test` (all green: gossip, gossip_nearby, gossip_bluey), `melos run analyze` (clean except gossip_nearby — 3 issues, see COR3-26 and MIN-20). **Every CRITICAL and MAJOR claim, and the load-bearing MODERATEs, were personally re-verified by the orchestrator against source, hop by hop**; adjusted and merged claims are listed in their own section.

**IDs:** `COR3-n` (correctness/robustness), `PERF3-n` (performance), `ARCH3-n` (CA/DDD), `MIN-n` / `OBS-n` (minor/observation) — audit ordinal 3, following the prior audits.

---

## Verdict

The core reconciliation algebra remains textbook-sound — version-vector domination, HLC monotonicity branches, deterministic total order, idempotent merge, the anti-livelock properties of the new `hasMore` continuation, and SWIM's ack discipline all re-verified clean. The two prior audits' remediations are **almost all genuinely in place** (30+ items re-verified fixed), the test suite is green, and the domain model is far better DDD than most codebases claiming the label.

However, this audit found **1 CRITICAL and 8 MAJOR defects**, and the pattern matters: the critical and several majors are **interactions between individually-correct recent fixes**. The headline (COR3-1): the contiguity guard (correctness-audit remediation), the monotonic version-vector high-water mark (H6 fix), and default-on auto-compaction (G3 fix) compose into a permanent, silent sync lockout for any late joiner on any compacted stream — with an endless futile re-send loop on the most bandwidth-poor link. It is reachable **today, under default config, in the shipped example**.

The second theme is **seam neglect**: the facade constructs its services without error callbacks (COR3-3), the `EntryRepository` interface still documents the pre-fix semantics whose implementation would resurrect two remediated HIGH bugs (COR3-8), the `MessagePort` failure contract is implemented with opposite semantics by the two in-repo transports (COR3-20), and channel membership — the product's own core concept — is enforced nowhere in the protocol layer (COR3-2).

On performance: no disaster, but the RX/TX hot paths do systematic redundant work — every message is fully decoded twice, most messages are encoded twice (pushes 1+P times), the merge path carries a fully redundant O(M·N) scan, and the BLE adapter re-resolves the GATT characteristic per 20–185-byte chunk. Individually tolerable at n≤8; together they multiply the cost of exactly the paths that run every second on the UI isolate.

Architecture: the five-layer structure is real and mostly honored; the substantive violations are the port interfaces homed in `infrastructure/` (contradicting ADR-010's own dependency rules), a dead application↔facade bridge, and gossip_bluey leaking third-party `bluey` enums through its domain port into consuming apps' presentation code.

Counts: **1 CRITICAL · 8 MAJOR · ~30 MODERATE · ~35 MINOR/OBSERVATION**, after merging duplicates across auditors.

## 🔴 CRITICAL

### COR3-1. Contiguity guard × monotonic version vector × auto-compaction: late joiners are permanently, silently locked out of every compacted stream — while full delta pages are futilely re-sent every round

- `gossip_engine.dart:1101-1104` — the guard accepts only a contiguous run starting at `ourVersion[author] + 1`:
  ```dart
  var next = ourVersion[author] + 1;
  ...
  if (entry.sequence != next) break; // gap — stop accepting this author
  ```
- `gossip_engine.dart:1369-1370` — a fully-dropped batch is **silent**: `if (newEntries.isEmpty) return null;` — no log, no error, nothing.
- `in_memory_entry_repository.dart:216-221` — the responder's VV deliberately never regresses on compaction (the H6 fix), so its digest advertises sequences it can no longer serve from 1.
- `coordinator_config.dart:150` — auto-compaction (the G3 fix) is **on by default**, every 5 minutes.

**Failure:** author A holds seqs 1..N on a stream with a pruning retention policy; compaction removes 1..k. A late joiner (or any peer offline past the retention window) has `ourVersion[A] = 0`; the responder's `entriesSince(∅)` returns survivors k+1..N; the guard requires seq 1, sees k+1, and drops the entire batch. The joiner's VV never advances, so every subsequent digest exchange re-detects "peer ahead" and re-triggers a full ≤30 KB `DeltaResponse` that is discarded again — **forever**, at gossip cadence, per (peer, compacted stream) pair, on a few-KB/s BLE link. In the shipped example this is live: `metadata` uses `CountBasedRetention(1)` and `presence` uses `TimeBasedRetention(30s)` (`chat_service.dart:57-68`) — a user joining a channel more than ~5 minutes after creation can **never receive channel metadata at all**, and every old-member↔joiner pair carries a permanent futile page-resend loop.

**Provenance:** the interaction of three individually-correct remediations (contiguity guard `7526336`, H6 monotonic VV, auto-compaction `b483f1d`). Not listed anywhere in the roadmap's deferred items — previously unknown.

**Fix direction:** the digest must advertise a **per-author floor** (lowest available sequence) alongside the high-water mark; a requester holding nothing below the floor explicitly fast-forwards its VV to the floor (accepting truncated history — correct semantics for retention-pruned streams) or triggers a snapshot/baseline transfer. Independently: emit an error/log when the guard drops a non-empty gapped run so this whole failure class is diagnosable. A stopgap (observability + a doc warning that retention policies break late-join) can land immediately while the floor is designed.

## 🟠 MAJOR

### COR3-2. Channel membership is enforced nowhere in the protocol layer; non-members ingest, store, and re-serve other channels' data
`gossip_engine.dart:492` — push fan-out iterates `peerRegistry.reachablePeers` (registry-wide, not per-channel); `handleDeltaResponse` (`:1340-1382`) merges straight into `entryRepository.appendAll` with **no** `_channels`/membership/local-stream check (contrast the request path, which checks both at `:1152`, `:1170`); `handleDeltaRequest` (`:1236-1251`) serves any channel to any requester. A peer in channel X but not Y receives Y's reactive pushes, stores the entries (`appendAll` creates storage via `putIfAbsent`), never advertises, never compacts (no aggregate → no retention), and serves them back on request — unbounded phantom storage plus disclosure across the membership boundary that CLAUDE.md defines as the product concept ("sync group with membership"). Routine since G1 made pushing the normal path, not just a byzantine case.
**Fix:** require a locally-known channel+stream in `handleDeltaResponse` (mirror `:1170`); scope push/digest fan-out to channel members; optionally check requester membership when serving.

### COR3-3. `Coordinator.create` wires no `onError` into ChannelService/PeerService — facade writes can vanish with zero signal, violating the project's own top rule
`coordinator.dart:295-310` — `ChannelService(... onEvent: ...)` and `PeerService(...)` get no `onError` (the engines do, `:342/:358`); `channel_service.dart:113-115` — `_emitError` is `onError?.call(error)`, a no-op. Reachable: `channel.getStream(unknownId)` then `append(...)` → `_appendEntryNow` emits into the void and **returns normally** (`channel_service.dart:372-382`) — the payload is gone, `await append()` succeeded, nothing on `coordinator.errors`. Same for membership ops on a concurrently-removed channel. Direct violation of "All errors must be logged or emitted via ErrorCallback."
**Fix:** pass `onError: coordinator._handleError` to both services; consider making the missing-stream append **throw** (caller misuse, same as the oversize `ArgumentError` at `:330`).

### COR3-4. Remove-then-recreate a channel reuses author sequences: first post-rejoin writes become permanently invisible, and colliding `(author, seq)` pairs diverge across peers
`channel_service.dart:179-187` — `removeChannel` clears entries and the sequence cache; re-`createChannel` with the same `ChannelId` restarts at seq 1 (`:384-386`). Peers that kept the channel hold `VV[us] ≥ old N`: their `entriesSince` filter and their contiguity guard both silently drop our new low-sequence entries forever. Worse: if we append before the peer's history resyncs back, we hold NEW `(us, 1)` while peers hold OLD `(us, 1)` — two different payloads for the same entry identity, undetectable (LogEntry `==` is author+sequence), never reconciled. And the peer's digest resurrects the entire "removed" history into the recreated channel. Reachable through the shipped example's leave/rejoin (`chat_service.dart:86`). `Coordinator.destroy()` documents exactly this hazard class for node identity (`coordinator.dart:1100-1103`); `removeChannel` says nothing.
**Fix:** preserve the per-channel author-sequence floor across remove/recreate, or document + steer to fresh ChannelIds on rejoin, or detect "peer VV exceeds my own latestSequence for my authorship" and emit a fatal, actionable error.

### COR3-5. gossip_bluey: peripheral fast-reconnect (supersession) is duplicate-rejected — the live replacement link is black-holed; permanent in star topology
The port's supersession path (`bluey_port_impl.dart:289-322`) replaces `_peripheralLinks[nodeId]` and emits only `PortPeerConnected` — no disconnect for the old link. `ConnectionManager._onPortEvent` (`connection_manager.dart:146-152`) sees `registry.contains(nodeId)` → treats the **live new link** as a duplicate → `_disconnectRoleGuarded` → `_rejectPeripheral` (`bluey_port_impl.dart:819-830`) marks the *new* link rejected and emits a role-matched `PortPeerDisconnected` → CM (`:201-205`) unregisters the peer entirely and drops its decoder. End state: B's side holds a healthy central connection; our side silently ignores every inbound write (`:217-221`) and has no outbound route. Ordering-conditional (`peerConnections` before `disconnections` — the ordering the port's own comments anticipate). In mesh, a later central-role reconnect may rescue it; a **star hub never initiates, so the spoke is black-holed permanently** while SWIM slowly suspects it.
**Fix:** treat a same-role peripheral connect for a registered NodeId as **supersession**: port emits `PortPeerDisconnected(old)` before `PortPeerConnected(new)`, or CM replaces (unregister→register, fresh decoder) instead of rejecting when incoming role == registered role.

### COR3-6. gossip_bluey: `connectTo` reports success for a registration-rejected connection — backoff never engages; GATT connect churn on every advertisement at the cap
`connection_manager.dart:120-128` — after `connectAndIdentify`, a bounded 16-turn wait for `registry.contains(nodeId)`, then **`return nodeId` regardless**. When the connect was cap- or duplicate-rejected, the caller gets success: `AutoConnectPolicy` (`auto_connect_policy.dart:143-145`) records the address as known and **clears backoff**; the next advertisement repeats the full connect→identify→reject→disconnect cycle, spamming `ConnectionLimitReachedError`, indefinitely. Manual-mode callers get a NodeId they can never send to (`ConnectionNotFoundError`).
**Fix:** after the wait, if `!registry.contains(nodeId)`, throw a typed `ConnectionRejectedException` so the policy backs off (and manual callers learn the truth).

### COR3-7. gossip_nearby: handshakes never time out; pending-handshake registry slots leak permanently; HARDENING_PLAN falsely records the fix as Complete
`connection_service.dart:369` registers the pending handshake; the only removal paths are `completeHandshake` and `cancelPendingHandshake` (`connection_registry.dart:47,53,77`) — and **`cancelPendingHandshake` has zero production callers** (grep-verified). Peer disconnects mid-handshake (`_onDisconnected:610-623` touches only `_handshakeStartTimes` + `_connections`), decode failure, send failure, or simply no response → the slot leaks forever. `_atConnectionLimit` (`:90-93`) counts `pendingHandshakeCount`, so with `maxConnections` configured each leak permanently consumes a slot until the transport rejects everything; without it, platform links are held open and metrics lie. `HARDENING_PLAN.md` Phase 1 claims "Complete… Stale handshakes are disconnected and cleaned up after 10s" — **no such code exists in HEAD or in any branch's history** (`git log -S` verified).
**Fix:** implement the plan's sweep in the existing retry tick (`_handshakeStartTimes` age check → `cancelPendingHandshake` + platform disconnect + event); correct the plan document.

### COR3-8. The `EntryRepository` interface still documents the pre-remediation semantics — a spec-conforming persistent implementation reintroduces entry resurrection, sequence reuse, and cross-peer ordering divergence
`entry_repository.dart:124-127` ("highest sequence… or 0 if none exist"), `:165-167` ("empty version vector if the stream has no entries"), `:141-151` (`removeEntries` — no mention of preserving anything), `:33-36` (ordering: "sorted by HLC timestamp" — no tiebreak). The actual invariants the engine now depends on — **monotonic high-water marks that survive compaction** (H6 fix) and **the full `LogEntry.compareTo` total order** (M3 fix) — exist only as comments on a private field of the in-memory class the docs tell you to replace (`in_memory_entry_repository.dart:44-53`). The docs explicitly direct production users to SQLite/IndexedDB implementations (`:52-57`); `SELECT MAX(sequence)`/`ORDER BY timestamp` is the natural reading and resurrects H6 (resurrection + permanent invisibility of new local entries after pruning) and M3 (divergent materialized state) wholesale, at auto-compaction cadence. `appendAll`'s duplicate semantics are similarly undefined (`:74-80` — "fails validation" never defined; skip-vs-throw changes engine behavior under COR3-9).
**Fix:** rewrite the interface contract: VV/latestSequence are monotonic over everything ever appended, must survive `removeEntries` and restarts, must not be derived from surviving rows; `getAll`/`entriesSince` must return `LogEntry.compareTo` order; duplicates must throw and `appendAll` must be atomic. Cheap (docs only), protects the library's primary extension point.

## 🟡 MODERATE

### Correctness / robustness — core

- **COR3-9. Overlapping merges interleave: partial `appendAll`, merged-but-unreported entries, errors mislabeled as peer corruption.** `handleDeltaResponse` has awaits between the VV read and `appendAll` (`gossip_engine.dart:1365-1378`); per-peer pending keying (the M3 fix) deliberately allows concurrent same-stream pulls from two peers; `InMemoryEntryRepository.appendAll` validates synchronously but inserts via `await append(...)` per entry (`in_memory_entry_repository.dart:148-150`), so "all-or-nothing" is violable under handler interleaving. Outcomes: a mid-batch `StateError` leaves a **partial batch applied**, aborts before `onEntriesMerged`, so entries sit in the repository but are never folded into materialized state and never re-fetched (VV covers them) — invisible until a rebuild; the error is caught by the dispatcher's blanket handler (`:847-858`) and blamed on the peer as `messageCorrupted`. **Fix:** serialize merges per (channel, stream) and/or make `appendAll` synchronous-atomic; stop mislabeling storage errors.
- **COR3-10. HLC accepts unbounded remote drift; one wrong device clock poisons the mesh.** `HlcClock.receive` takes an unconditional max (`hlc_clock.dart:86-97`); `Hlc` enforces no upper bound on `physicalMs` despite documenting 48 bits (`hlc.dart:56,65-87`); the engine updates the clock **before** the contiguity filter (`gossip_engine.dart:1358`), so even dropped entries poison it. A single peer with a far-future clock (misconfiguration, not malice) permanently advances every node; `TimeBasedRetention` then computes a far-future cutoff and prunes all sanely-timestamped entries at the next 5-minute compaction — and the monotonic VV ensures they are never re-fetched (COR3-1 makes it worse). Exposure in the shipped example is presence-only; any app with `TimeBasedRetention` on durable data gets mesh-wide loss. **Fix:** bound drift in `receive` (reject/clamp + error), enforce the 48-bit bound at decode, move `_updateHlcFromEntries` after the filter.
- **COR3-11. Push-pull reciprocation (M1 fix) spams `protocolError` for every non-shared channel, every round.** The reciprocation path (`gossip_engine.dart:792-800`) feeds the sender's full digest list into `_computeDeltaRequests`, which emits `ChannelSyncError('unknown channel')` per unknown channel (`:1153-1161`). Any two peers with partially-overlapping channel sets → a permanent 1–2/s false-alarm stream drowning real errors. (The serve path handles the same case silently and correctly.) **Fix:** trace-level skip, like unknown streams (`:1170-1177`).
- **COR3-12. The G5 "in-sync" signal wedges permanently; `clearPendingRequests` is dead code.** Pending pulls are only lazily expired when the same (peer, channel, stream) key is re-evaluated — never once the peer is removed or silent. `Coordinator.removePeer` clears the probing hold but not pending deltas (`coordinator.dart:710-714`); `clearPendingRequests` (`gossip_engine.dart:1415-1422` — "Call this when a peer disconnects") has zero production callers, and the test named `clearPendingRequestsForPeer…` exercises a method that does not exist (whole-map clear at `gossip_engine_message_handling_test.dart:755`). Result: `gossipSyncActivity.isQuiescent` reads false forever after a peer departs mid-pull — breaking the exact UI the feature shipped for — and the map grows under NodeId churn. **Fix:** clear per-peer pending entries in `removePeer`; exclude expired entries from `outstandingPullCount`.
- **COR3-13. One throwing materializer starves its siblings of the batch, permanently.** `foldEntries` awaits each materializer's enqueue sequentially (`materialization_service.dart:99-110`); `_enqueue` returns the op's own error future (`:71-78`), so the first materializer's `fold`/`save` throw aborts the loop — later materializers never see the batch, and the next successful fold advances their cursor past it. Silent divergence until reset/restart. **Fix:** enqueue all, then `Future.wait`; report per-materializer errors.
- **COR3-14. App materializer exceptions in the merge path are mislabeled, suppress `EntriesMerged`, and abort the catch-up continuation.** `_handleEntriesMerged` (`coordinator.dart:483-488`) folds with no try/catch; the exception propagates through the engine's `await onEntriesMerged` into the blanket catch (`:847-858`) as `messageCorrupted` "Malformed gossip message from <peer>"; entries are stored but the app never hears, and `hasMore` draining stalls to periodic cadence. **Fix:** catch around the fold, emit `StorageSyncError`, still emit `EntriesMerged`.
- **COR3-15. `compactAll` has no per-stream error isolation.** One throwing retention policy / repo failure / materializer `initial()` aborts the entire pass (`channel_service.dart:665-673`); the tick reschedules and hits the identical failure every 5 minutes — streams later in iteration order are never compacted again, surfaced only as a repeating generic error. **Fix:** try/catch per stream.
- **COR3-16. `createChannel` on an existing ID silently resets the aggregate.** No existence check at either layer (`channel_service.dart:136-140`); membership wiped, stream registrations + retention dropped (entries survive but stop being advertised until streams are recreated), spurious `ChannelCreated`. The shipped example *relies* on this as "join" (`chat_service.dart:86`), entrenching the footgun and feeding COR3-4. **Fix:** get-or-create semantics (no-op when exists) or throw.
- **COR3-17. `CachingChannelRepository`: cache mutated before write-through, no rollback; `findById` TOCTOU loads two aggregate instances.** `save` puts into the cache then awaits the inner (`caching_channel_repository.dart:40-43`; mirror problem in `delete`/`clearAll`); concurrent cache misses both load and last-write-wins (`:28-37`) — the identity-map invariant the class exists for. Both unreachable with the in-memory inner; real for the persistent repos the class was built to wrap. **Fix:** write-through first / evict on failure; cache the in-flight future.
- **COR3-18. A disposed coordinator still accepts writes.** Facades keep a live `ChannelService` after `dispose()`; `append` writes the repository and advances+persists the HLC, its event dropped at the closed controller — durable-but-orphaned data with no error (`coordinator.dart:1057-1087`, `channel_service.dart:339-353`). **Fix:** `_disposed` guard throwing `StateError`, consistent with `start`/`stop`.
- **COR3-19. `PeerService.removePeer`'s delete bypasses the per-peer save queue.** `_deletePeer` calls `repository.delete` directly (`peer_service.dart:100-103, 217-229`); an in-flight save past its registry check can land after the delete → removed peer resurrected in a persistent `PeerRepository` on restart. **Fix:** route the delete through the same chain.
- **COR3-27. HLC-tie blind spots in materialization.** (a) The init cursor filter is strictly-greater (`materialization_service.dart:219` — `e.timestamp > c`): an entry folded-but-not-yet-persisted whose timestamp *equals* the crash-time cursor is skipped forever on restart. (b) The out-of-order flag compares raw HLC against the tail (`gossip_engine.dart:1385-1387`) while the store inserts by full `compareTo` — an equal-timestamp entry sorting before the tail is inserted before it but folded incrementally after it: live state diverges from any rebuild for non-commutative folds. **Fix:** cursor and tail comparisons on `(timestamp, author, sequence)`.
- **COR3-28. `DeltaRequest.since` is still a full, unbudgeted version vector** (`gossip_engine.dart:1206-1213`) — the algorithm audit's H4 explicitly recommended budgeting it alongside digests; only digests were done. Latent: a node whose own VV for one stream exceeds the frame limit can advertise (rotation) but can never *pull* that stream — permanent, surfaced only as generic per-round send failures. **Fix:** same treatment as digests (bound, or delta-encode VVs).
- **COR3-30. `LogEntry.payload` is a mutable `Uint8List` held by reference, and the append pipeline defers reading it.** No copy anywhere from `EventStream.append` through the queued `_appendEntryNow` to the codec (`log_entry.dart:44,49-62`; `channel_service.dart:337-350,397-401`). An app reusing a scratch buffer after `unawaited(stream.append(buf))` persists/syncs corrupted bytes — and since `==` is author+sequence, local and remote copies can silently differ. **Fix:** copy at the facade boundary (or `LogEntry` constructor).

### Correctness / robustness — transports

- **COR3-20. The `MessagePort` failure contract is ambiguous and the two transports implement opposite semantics — bluey's defeats the engine's rollback.** The doc says "No exceptions on failure" (`message_port.dart:94`), yet the engine's only failure signal is a throw (`gossip_engine.dart:869-884` → pending-flag rollback at `:1128-1132`); gossip_nearby completes send futures with errors, gossip_bluey completes them as **success** after emitting on its own error stream (`connection_manager.dart:352-367`) — so on the shipping transport a failed delta send holds the pending flag for the full timeout and records `recordMessageSent`. The doc's `implements` example doesn't even compile (`:60-88` vs required `pendingSendCount` members). **Fix:** define the contract (recommend: throw = immediate failure), align bluey, fix the example.
- **COR3-21. (H11 sub-issue, still open) A cap/duplicate-rejected inbound bluey peer keeps a live link and gossips into the void indefinitely.** bluey has no per-client peripheral disconnect (`bluey_port_impl.dart:807-818`, honest doc); the rejected initiator's writes are acked at GATT level and silently dropped above (`connection_manager.dart:217-221`); it registers us as healthy and burns a cap slot + radio forever. Combined with COR3-6, both sides at a cap boundary degrade permanently. **Fix:** application-level rejection frame (outbound send on the rejected link works), or a bluey per-client disconnect API.
- **COR3-22. bluey: no timeout on `port.sendData`** (`connection_manager.dart:349`) — one hung GATT write wedges that peer's drain loop; disconnect events can't unstick it (the identity check runs only between awaits); high-priority pings queue behind it; queues are depth-unbounded. **Fix:** bounded `.timeout(...)` per chunk.
- **COR3-23. bluey: unhandled-error surfaces (the prior M5 class, transport edition).** `_onPortEvent` has no try/catch and `_portSub` no `onError` (`connection_manager.dart:41,134`); `AutoConnectPolicy` subscribes without `onError` while `DiscoveryService` forwards scan errors (`auto_connect_policy.dart:101`, `discovery_service.dart:63-66`) → every transient scan error is an uncaught zone error; notification/state subscriptions likewise (`bluey_port_impl.dart:551-561`) — a stream error silently kills inbound data for a still-registered peer. **Fix:** wrap the handler; add `onError` + logging throughout.
- **COR3-24. nearby: `dispose` leaves the send pipeline live.** No queue drain, no closed-guards (`connection_service.dart:238-243`); a post-dispose send failure throws `StateError` on the closed error controller **before** completing the sender's completer — awaiter hangs, remaining queue stranded. bluey demonstrates the fix (closed-guards + dispose-time flush). 
- **COR3-25. nearby: delivery outcomes are invisible.** `onPayloadTransferUpdate` is an empty lambda (`nearby_adapter.dart:252`) — the only transfer-failure signal is discarded while the sender's future completed at enqueue; non-BYTES payloads dropped silently (`:286`); `requestConnection`'s `false` return ignored (`:195-203`). Violates the no-silent-errors rule at the transport boundary.
- **COR3-26. nearby: `acceptConnection.catchError` handler returns void for a `Future<bool>` → runtime `TypeError` on the error path.** `nearby_adapter.dart:246-268`; plugin signature verified `Future<bool>` (`nearby_connections-4.3.0/lib/src/nearby.dart:284`). When `acceptConnection` rejects, the handler's side effects run, then a `TypeError` propagates as an unhandled zone error masking the platform error. This is one of the 3 live analyzer findings, and the exact path HARDENING_PLAN Phase 2 claims fixed. **Fix:** `return false;`.
- **COR3-29. bluey mesh: no pre-connect tie-break → every mutual connect holds TWO physical GATT links; CLAUDE.md documents a tie-break and star discovery filter that don't exist.** No tie-break code exists (grep; `ScanCandidate` carries no NodeId so none is possible pre-connect); post-H9, mutual connect converges to both centrals alive with peripheral views "rejected but physically up". At n=8: up to 14 concurrent links per device vs ~7-8 platform ceilings — connection storms at exactly the documented target scale, invisibly (registry says 7). Root CLAUDE.md: "Tie-break by `NodeId.value` ensures one initiator per pair" and "spokes call `startDiscovery(filter: hubId)`" — `startDiscovery()` takes no filter (`bluey_transport.dart:297`). **Fix:** embed NodeId (or a hash) in the advertisement for a pre-connect tie-break; add the star filter or fix the docs.

### Performance

- **PERF3-1. Every incoming message is fully decoded twice; the wire's type byte — designed for "fast message type discrimination" — is never used.** Both engines subscribe to the same stream and each runs `_codec.decode(message.bytes)` on everything (`gossip_engine.dart:776`, `failure_detector.dart:724`): the FailureDetector JSON-parses and base64-decodes every 30 KB delta page and discards it; the engine decodes every ping. `decode` also copies the buffer (`protocol_codec.dart:94` `sublist`). ~1–2 ms + ~100–200 KB garbage per large page, ×2, on the UI isolate, at link speed during catch-up; malformed input emits **two** `messageCorrupted` errors. **Fix:** dispatch on `bytes[0]` before decoding; `sublistView`.
- **PERF3-2. TX serializes everything twice — and reactive pushes 1+P times.** Size-check encode then send encode for digests (`gossip_engine.dart:637-638` → `:866-867`), per-entry encode then whole-message re-encode for delta pages, and `_flushPendingPushes` encodes once for the size check then `_sendMessage` re-encodes per peer (`:503-506`) — up to 8 encodes of one message. The codec itself triple-copies (`protocol_codec.dart:131` `Uint8List.fromList(utf8.encode(...))` + `:73-76` setRange). (`_sendPingRequests` shows the right pattern — encode once, reuse.) **Fix:** let `_sendMessage` take pre-encoded bytes.
- **PERF3-3. The merge path is O(M·N) with a fully redundant scan — in the only shipped `EntryRepository`, which the example uses in production.** `appendAll` builds an O(N) validation set, then each `append` **re-scans the whole list anyway** (`in_memory_entry_repository.dart:66-68,135-150`). A 130-entry page into N=5,000 ≈ 325k comparisons + 5k tuple allocations, ~1–5 ms synchronous per page, recurring, growing with history; every local append also pays an O(N) scan. **Fix:** O(1) fast-path via the latest-sequence cache (or a per-stream (author,seq) hash set); skip the redundant scan from `appendAll`.
- **PERF3-4. Any out-of-order merge triggers a full O(N) materializer rebuild, inline in the merge path.** Trigger is routine under concurrent multi-author writes (`gossip_engine.dart:1384-1387`); rebuild refolds the entire stream (`materialization_service.dart:243-265`) and delays the catch-up continuation. Cost-of-correctness for non-commutative folds — but at N=5k with app-defined folds it's tens of ms on the UI isolate, recurring. **Fix:** merge-position-aware repair from a checkpoint, or a commutativity opt-in that keeps the incremental path.
- **PERF3-5. bluey central TX re-resolves the GATT service + characteristic and re-derives the UUID for every chunk** (`bluey_port_impl.dart:641-666`): a 30 KB message is ~165 chunks at MTU 185 and ~1,540 at the 20-byte fallback — each paying `services()` + `firstWhere` with fresh lowercased strings, although the characteristic was already resolved at registration (`:531-551`). **Fix:** cache it on `_CentralLink`.
- **PERF3-6. nearby's send queue is one global lane pair for all peers** (`connection_service.dart:78-81,196-212`): one stalling endpoint head-of-line-blocks high-priority SWIM pings to **every other peer** — the regime prior-H1 existed for. bluey's per-peer queues are the proven in-repo fix; nearby has no frame-contiguity constraint forcing a global lane.

### Architecture (CA/DDD)

- **ARCH3-1. The port interfaces live in `infrastructure/`, inverting the dependency rule for domain, protocol, and application — and ADR-010 codifies the contradiction.** `TimePort`/`MessagePort` are pure abstract ports (verified) consumed by inner layers (`gossip_engine.dart:19-20`, `failure_detector.dart:13-14`, `time_source.dart:1` — whose own doc claims it exists to prevent exactly this). ADR-010 simultaneously places them in infrastructure (`:69`) and declares "Protocol layer: depends on domain" (`:164`) and "Domain defines interfaces; infrastructure implements" (`:171`). **Fix:** move the interfaces to `domain/interfaces/` (repositories already model this correctly); keep implementations in infrastructure; amend ADR-010.
- **ARCH3-2. The declared layer diagram diverges from reality, and the ADR's named application↔protocol bridge is dead code that imports the facade.** No application file imports protocol; the facade constructs and drives the engines (composition root — fine, but not what ADR-010 draws). `CoordinatorSyncService` — ADR-010's listed component — has zero production consumers and imports `../facade/coordinator.dart` from the application layer (`coordinator_sync_service.dart:4`); its interface's claim that "protocols depend on this interface" is false. Its `getPeer` is also O(n) against an O(1) registry. **Fix:** delete both files + test (or genuinely invert); redraw ADR-010; fix the "ChannelFacade/EventStreamFacade" naming drift.
- **ARCH3-3. Application services import infrastructure codecs in both transports; wire-format knowledge executes in the application layer.** `connection_service.dart:15` (+ byte dispatch on `WireFormat.typeOffset` at `:425-440`); `connection_manager.dart:15-16` (+ `FrameDecoder`/`FrameEncoder` calls). Contradicts nearby's own ADR-005. **Fix:** the codecs define the packages' *own* wire protocols — home them as protocol/domain services (the core package's `protocol/` layer is the in-repo precedent), or inject behind an application-owned interface.
- **ARCH3-4. nearby has bidirectional application↔infrastructure coupling** — `nearby_message_port.dart:6` imports the concrete `ConnectionService` and wires a public mutable callback slot (`connection_service.dart:96`); combined with ARCH3-3 the layer graph has edges both ways. bluey's `MessageDispatcher` seam is the in-repo fix (but that interface is itself homed in infrastructure). **Fix:** dispatcher interface in application/domain in both packages.
- **ARCH3-5. bluey leaks third-party `bluey` enums through the domain port and public facade — demonstrably forcing consumers onto the underlying library.** `bluey_port.dart:3,98-117` exposes `bluey.AdvertisingState`/`bluey.ScanState` (the same file's doc: "Speaks only in domain types"); `bluey_transport.dart:183-199` re-exposes them; the example app imports `package:bluey` in **4 files** including presentation widgets purely to name these enums. The package already shows the correct pattern (`BluetoothAdapterState` — an explicit translation VO). **Fix:** `AdvertisingLifecycle`/`ScanLifecycle` domain enums mapped in `BlueyPortImpl`.
- **ARCH3-6. The protocol layer mutates `PeerRegistry` (and writes entries/clock state) directly, bypassing the application services whose docs claim to own those paths.** `failure_detector.dart:552,575,587,952`, `gossip_engine.dart:598,761,773,871,1378,1442` — none via `PeerService`/`ChannelService`; both services' "Used by: Protocol services" doc claims are false; consequence: with a persistent `PeerRepository`, every SWIM status/contact/metric change is silently unpersisted (only add/remove hit storage). Semi-deliberate (peers documented transient) but undeclared. **Fix:** document protocol-driven peer state as memory-only by design (and simplify PeerService), or route mutations through it; fix the doc lies either way.

## What is genuinely healthy (verified — protect on purpose)
