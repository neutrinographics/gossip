# Record where the Dart library and its Kotlin twin diverge, with a verdict

**Track:** Kotlin port   **Depends on:** nothing

## What this is

The Dart library (`packages/gossip`) and its standalone Kotlin port
(`gossip-kt`) implement the same protocol twice, in two languages, by two
different hands at two different times. Every time a review of one
compares it against the other, it turns up a place where they made a
different choice — sometimes a deliberate, permanent one, sometimes an
accident nobody has revisited. This file is the durable register of those
differences: one row per divergence, a plain read of where each side
stands, a verdict on which is better (or that the difference is fine to
keep), and where the fix (if any) already lives.

The practice this register exists to support is bidirectional: when a
review of a Dart change surfaces a divergence, or a review of a Kotlin
change does, the divergence gets a row here before the conversation that
found it is forgotten. Adoption can flow either way — most of the time the
port is catching up to the original, but sometimes the port found the
better shape and the original should adopt it.

## Why it matters

Two implementations of one protocol drift apart silently unless someone
writes the drift down. A code review that spots a divergence and doesn't
record it is a fact that evaporates the moment the branch merges — the
next person to touch either side has no way to know the difference was
ever noticed, let alone judged. Recording it with a verdict turns a
one-time observation into something the other library can act on whenever
it's next convenient, and stops the same divergence from being
"rediscovered" and re-litigated in a future review.

## The register

| Divergence | Where each side stands | Which is better | Recommendation |
|---|---|---|---|
| Frame dispatch | kt chains membership→sync through one dispatch point: exactly one report per bad frame, and a `NotMine` result short-circuits before the other codec ever tries to parse. Dart runs both engines' codecs independently over the full incoming stream, so a byte neither codec recognizes throws in both and is reported twice per frame — a known flaw the wire-versioning spec's §5.2 rollout-ordering constraint has to work around rather than fix. | kt | Dart should adopt a single dispatch seam that tries one codec, only falls through to the other on a sibling (`NotMine`)-shaped result, and reports malformed frames exactly once. |
| Decode failure contract | kt's decode result is a sealed type with three cases — decoded, not-mine (sibling family, fall through), and malformed (with diagnostic detail). Dart represents the same three outcomes as: `null` return for "not mine", a thrown exception for an unrecognized type, and an `onError` callback catch at the call site to turn that exception into a report. | kt | kt's shape is more explicit and type-safe — the caller can't forget to handle a case the way it can forget to catch an exception. Candidate for Dart to adopt, most naturally alongside the single-dispatch-seam change above since both touch the same call sites. |
| Frame classifier | kt's frame classifier (`FrameFraming`) is a non-throwing sealed result carrying typed diagnostics for each way a frame can fail to classify. Dart's `frameTypeOffset` throws and otherwise returns a plain offset. | kt is richer | Optional. Dart already adopted the differentiated per-class marker diagnostics this classifier produces (the "unregistered wire version N" style messages); moving to a non-throwing sealed *shape* on top of that is a nice-to-have, not a gap that causes wrong behavior. |
| Version-vector explicit-zero handling | Dart drops explicit zero entries at construction (`VersionVector`'s normalization), on the rationale that keeping them lets structural and semantic equality diverge for what should be the same vector. kt preserves explicit zero entries as written. | Tolerated asymmetry, with one real consequence | Decode is genuinely unaffected: absent and explicit-zero are the same value to both sides. **But encoding is not symmetric, and that has bitten a consumer.** Dart cannot reproduce a frame containing `"node":0`, so a byte-exact comparison of Dart's *output* against a kt-sourced golden vector containing an explicit zero can never pass — found 2026-08-31 while bumping the app's pin, where a translator round-trip test failed for exactly this reason. The fix there was to compare that one direction semantically and to leave the golden untouched, since the golden is truthful about what kt emits. Anything byte-comparing Dart output against kt-captured vectors needs to know this. The asymmetry itself remains deliberate and likely permanent. |
| Delta batching | kt's original (pre-wire-versioning-batch) delta emission batched multiple messages into one envelope. That shape was the inspiration for the budget-aware batch-envelope wire-efficiency item, which already exists on the roadmap. | N/A — idea already captured | Don't duplicate; see [Coalesce wire traffic into fewer radio wakeups](engine-message-coalescing.md) ("batched delta forms"), which carries this forward for both libraries. |
| Entry insertion order | kt's `findInsertIndex` (`in_memory_entry_repository`-equivalent) orders entries by timestamp only when inserting. Dart orders by the full `(timestamp, author, sequence)` total order. | kt is worse | This is a real correctness gap, not a style difference: two peers whose materializers fold entries in different arrival order for an HLC tie will converge to different derived state. The fix is already routed — it's flagged as a KT-E candidate in the Kotlin port's batch sequence (`docs/superpowers/specs/2026-08-28-kt-port-dart-fix-inventory.md`, item 13 / "M3"). This row exists so the divergence has a home outside that plan file too. |
| Pending-request expiry | Dart uses an adaptive expiry window for pending delta requests, scaled between roughly 2 and 30 seconds based on measured round-trip time. kt used a fixed 5-second expiry. | Dart, converged | **Closed** by Batch KT-B (2026-08-29): kt ported the adaptive RFC-6298-style tracker (2–30s window, release-on-send-failure); see `docs/plans/2026-08-29-kt-batch-b-sync-depth.md` in the gossip-kt repository. |
| Merge-path serialization | Dart's `DeltaMerger`/`KeyedTaskChain` protects against an interleaving hazard across concurrent merge suspensions. kt's single-collector receive loop structurally excludes that hazard — one coroutine processes one inbound message at a time — and Batch KT-B (T1) additionally closed the one gap that could have broken the assumption: an unguarded `Coordinator.start()` could double-start the collector and fork the loop; it now has start-idempotence. | Tolerated architectural difference | No action for kt. If Dart ever adopts a single-dispatch receive loop (see the frame-dispatch row above, which is already a candidate for that shape), the `KeyedTaskChain` tax could be reassessed then — not before. |
| `appendAll` phantom-stream registration | Both libraries' `appendAll` called `getOrPut` (stream-map lookup-or-create) before validating the batch, so a batch rejected in full still left behind an empty stream entry — visible to later reads as a stream that was never actually written. kt fixed it in Batch KT-B (`fb0cd32`, T2 fix round): validation now precedes the `getOrPut`. | kt (now) | **Fix in Dart** — this is a real, if minor, bug carried from the shared original shape, not a style choice. Also tracked as an actionable line in [Sweep the remaining minor audit findings](health-minor-findings-sweep.md). |
| Ingestion guard for unheld streams | Dart's `GossipEngine` refuses inbound deltas for a channel/stream it doesn't currently hold (`gossip_engine.dart:1532-1539`). kt lacked this repository-level gate entirely. | Dart, converged | **Closed** — kt converged in Batch KT-B (`fb0cd32`, T2 fix round): it now mirrors Dart's refusal exactly (trace-silent, matching log level). |
| Test-strength flow-backs (three examples) | (1) kt's authorship-floor pin (Batch KT-B, T4) asserts at the allocation level (the actual sequence allocator's output); Dart's equivalent pin asserts only at the mark level. (2) kt's crown integration scenarios (T7) seed an error sink listening from every node from t=0; Dart's per-node late-listen setup can miss errors raised before a listener attaches. (3) kt has a small unit pin for gap-reopening on `clearPendingRequests` (T6 ride-along) that Dart's suite has no equivalent of. | kt, in all three | Adopt kt's stronger versions in Dart's test suites — none of these are behavior changes, only discriminating-power gaps in the pins themselves. |
| Event-dispatch placement | Dart emits domain events in-aggregate (e.g. `PeerRegistry.onEvent`). kt emits them from an application service wrapping the aggregate (`PeerService`) — established when Batch KT-B's PeerDirectory ACL (T5) required rewiring event dispatch through the service layer. | Structural, not a defect | No fix, but record the rule the port surfaced: any kt ACL placed over a service-wrapped aggregate MUST route writes through the service, or event dispatch dies silently — the aggregate's own `onEvent` never fires if a caller reaches the aggregate directly. |
| Thread-safety posture (domain services on a hot/arbitrary-caller boundary) | Dart's single-isolate execution model means no domain service needs internal synchronization (ADR-001). kt's `PendingPullTracker` (Batch KT-B, T6) sits on a boundary where the Coordinator's non-suspend `stop`/`pause`/dispose calls race the receive loop's arbitrary-coroutine calls, with no happens-before between them — it and the matching `_reportedGaps` guard are internally monitor-guarded (plain JVM `synchronized`) rather than deferring to a `Mutex`, which was rejected because it would force suspend-ness onto the otherwise non-suspend facade methods. | N/A — necessitated by the platform | Record as kt's default pattern for any future domain service sitting on this same arbitrary-caller/hot-path boundary: guard the whole surface with a plain monitor (not a partial guard), and don't reach for `Mutex` if it would infect an otherwise-synchronous facade. |
| Partition primitive | Dart's test harness (`TestNetwork` DSL) can partition a link one-way or two-way while preserving each side's stale state, closely modeling a real radio dropout. kt's integration tests modelled peer loss via `peers.remove()`/`peers.add()`, which scrubs all state on removal — it could not represent a peer that's unreachable but still believed present. | Dart stronger, **now closed and overtaken** | **Closed** by Batch KT-D (2026-08-30): kt's bus grew directional `blockLink`/`healLink` and `partitionNode`/`healNode`. kt then went further than Dart — see the heal-in-place row below. |
| Per-cycle interval recomputation | Dart's periodic loops recompute their delay every cycle (`GenerationScheduler.nextDelay()` is called fresh before each wait), so adaptive intervals actually adapt while running. kt's gossip loop computes `effectiveGossipInterval()` once at start (`GossipEngine.kt:132`) and `schedulePeriodic` freezes it thereafter — the "adaptive" interval holds its start-time value for the life of the loop. | Dart stronger | Batch KT-C ported `GenerationScheduler` for the auto-compaction loop (2026-08-30); migrating the gossip and failure-detector loops onto it (restoring per-cycle adaptation, mirroring Dart's CC5-7 consolidation) is the follow-up. Surfaced by the 2026-08-30 scoped audit. |
| nextDelay error uniformity | kt's `GenerationScheduler` invokes `nextDelay()` inside the loop coroutine's try, so a throwing `nextDelay` is uniformly a scheduling error on every cycle. Dart's calls it as the argument to `timePort.delay(...)`: on the FIRST cycle the throw escapes `start()` synchronously; on later cycles it reaches `onSchedulingError` — two different failure surfaces for one defect. | kt better | Fix Dart to route the first-cycle `nextDelay` throw through `onSchedulingError` too (move the call inside the chain). Latent Dart defect found by the KT-C C1 review; queue with the Dart minor-findings sweep. |
| Compaction-interval disable idiom | Dart disables auto-compaction on `compactionInterval == null` OR `<= zero`. kt disables only on `null` and REJECTS non-positive values in the config's fail-fast guard — a meaningless timing is an error, not a silent off-switch. | kt stricter (deliberate) | Candidate Dart flow-back: reject non-positive `compactionInterval` instead of silently treating it as disabled. Decided in the KT-C plan (ruling 5). |
| Auto-compaction in local-only mode | Dart's compaction loop is gated on `timePort` presence, so local-only coordinators never auto-compact. kt always has a TimePort (`RealTimePort` default), so retention is enforced even without a mesh. | kt arguably better (deliberate) | Retention deserves enforcing locally too; consider giving Dart's local-only mode a real timer for compaction. Decided in the KT-C plan (ruling 6). |
| Channel-level manual compact facade | kt's `Channel.compact()` fans out over every stream in the channel and returns a per-stream result map; Dart exposes only the stream-level `EventStream.compact()`. | kt richer | Candidate Dart flow-back: add a channel-level compact fan-out to Dart's `Channel` facade. Noted at KT-C close. |
| SWIM indirect probing | **Dart works; kt's is inert.** Dart's `FailureDetector` subscribes with `Stream.listen`, which does not await its handler, and Dart runs two independent subscriptions (detector and engine each listen separately) — so an intermediary's `_handlePingReq` can await the target's Ack while the same subscription keeps delivering. kt's `Coordinator.start` collects `messagePort.incoming` in a SINGLE suspending `Flow.collect` (a documented invariant, load-bearing for `GossipEngine`'s unsynchronized merge state); `handlePingReq` is called inside that lambda and suspends in `awaitAckWithTimeout`, but the target's Ack can only arrive through the very collector it is blocking. The intermediary therefore always times out at `INTERMEDIARY_TIMEOUT`, never forwards the Ack, and `cleanupPendingPing` has already dropped the entry by the time a late Ack could match. | Dart — this is a live kt defect, not a style difference | Behavioral consequence: a one-way-deaf pair with a healthy relay keeps both views REACHABLE in Dart but degrades to SUSPECTED in kt — SWIM's indirect-probe path buys kt nothing today. **Needs its own task**, not a ride-along: the naive fix (`launch` per routed message) is unsafe because `_nextSequence` and `_pendingPings` are unguarded mutable fields already touched from two coroutines, so a third concurrent path needs a guard; and it changes a documented concurrency invariant. Found and mutation-verified in Batch KT-D (`failedProbeCount` 4 → 0 once the collector routes concurrently), then re-derived independently from source in review. One Dart scenario (`asymmetric_partition_test.dart`'s relay test) remains untranslatable in kt until it is fixed. |
| Partition heal semantics | Dart's `TestNetwork.partition` UNREGISTERS the port and `heal` calls `reregister()`, so a "healed" node is really a re-registration — Dart's own KDoc concedes it "may need probe rounds to recover". kt (Batch KT-D) blocks links in place, leaving ports registered, so the node that rejoins is the same node with the same coordinator state. | kt | Dart should adopt block-in-place. It is the only shape in which "a partition heals" proves anything about recovery: Dart's own peer-status suite has to call `addPeer` on both sides after healing to stand in for a transport reconnection, which means it cannot prove heal-in-place recovery at all. |
| Congestion backpressure in tests | Dart's bus exposes `setSimulatedPendingCount`/`…ForPeer`, so a congestion test pins the gate against a DECLARED number. kt has no such knob — `pendingSendCount` can only be the link's real held-queue depth. | kt | A gate pinned against a declared number pins the test, not the production code. kt's congestion suite (Batch KT-D) pins the shipped gate at `GossipEngine.kt:229` for real, mutation-verified. Candidate Dart flow-back. |
| Reactive push on local append | Dart pushes new entries to reachable peers immediately (a `DeltaResponse` with no preceding `DeltaRequest`); kt is pull-only, so a post-start write waits for the next digest round. | Dart, on latency | Do NOT open a second home for this: the port is already carried by [Port the wire-efficiency behaviors to the Kotlin library](kt-port-wire-efficiency.md). Recorded here only because Batch KT-D's scenario translation depends on knowing it — kt's congestion bound is "gated digests only" where Dart's is "one ungated push plus gated digests" (same total), and it is why kt reaches `DeltaResponse` via the solicited path in the duplicate-frame scenarios. |
| Simulated-clock dispatch | Dart's `TimePort.schedulePeriodic` takes a NON-suspending callback, so its fake clock fires boundaries synchronously in-line, never wedges, and propagates a callback throwable straight to the advancing caller. kt's takes `suspend () -> Unit` and originally AWAITED it, so a probe against an unresponsive peer deadlocked the advance that fired it. Batch KT-D converted kt to fire-and-forget per-boundary dispatch with a port-owned scope, an explicit `awaitCallbacksIdle`, `close()`, and errors routed to the reporting node's sink. | Dart on determinism; kt now has the better escape hatch | kt's suspend-typed callback is the root cause and remains a genuine race window Dart does not have. Conversely Dart has no `advanceTimeOnly`, so a Dart test taking a multi-hour jump on a running node owes proportionally many synchronous firings with no way to say "move the wall clock only" — kt's boundary-consuming `advanceTimeOnly` is the better primitive and is a candidate port back to Dart. |
| Sub-millisecond periodic interval | Dart rejects `interval.inMilliseconds <= 0` on its in-memory time port. kt rejected only `> Duration.ZERO`, so a sub-millisecond interval truncated to zero whole milliseconds; Batch KT-D converged `InMemoryTimePort`, but `RealTimePort` still uses `> Duration.ZERO` and the `TimePort` interface documents neither rule. | Converged on one implementation; a documentation gap remains | Minor. State the rule on the `TimePort` interface (Dart states it on the implementation too), and decide whether `RealTimePort` should match. |
| `getOrCreateStream` is not get-or-create in kt | kt's `Channel.getOrCreateStream` delegates to `ChannelAggregate.createStream`, which THROWS `DomainException` when the stream already exists — so both the method name and its own KDoc ("Gets or creates a stream") are false. Dart's is genuinely get-or-create, and Dart's own test support depends on that. | Dart | Real production issue, same defect class as the `createChannel` get-or-create fix shipped in Batch KT-D. Make kt's behavior match its name, or rename the method. Found by the KT-D harness (which works around it), confirmed independently in review. |
| Per-stream append serialization | Both libraries serialize same-stream local appends so concurrent callers all succeed with contiguous sequences — Dart with `KeyedTaskChain`, kt (Batch KT-D) with a per-(channel, stream) `Mutex` map. Ordering (FIFO) and failure isolation (the next waiter always proceeds) are equivalent. The difference is cleanup: Dart removes a key once its queue drains, so its footprint returns to zero under any stream churn; kt's map never evicts. | Dart, structurally | kt's is safe only while the "streams are provisioned, not created per message" assumption holds — assumption-safe rather than structurally safe. Evict kt's entry when uncontended; a `dispose()` clear shipped in Batch KT-D as a partial measure. |
| Secondary materializer fold failures | Both libraries now run every materializer's fold to completion and surface only the FIRST failure; a second materializer failing on the same batch is dropped with no log and no error-callback emission (Dart: `Future.wait(eagerError: false)`; kt: first-failure accumulation, Batch KT-D). | Neither — a SHARED gap | Sits in tension with both libraries' "no silent errors" rule. Consider emitting the non-first failures through the error sink in BOTH libraries. |
| Which fold failure is reported "first" | Dart iterates its materializer states in registration/insertion order, so the reported first failure is deterministic. kt iterates a `ConcurrentHashMap`-backed snapshot, so with multiple simultaneous failures the reported one is hash-bucket-order dependent. | Dart, marginally | Only matters in the multi-simultaneous-failure case. If kt ever needs a deterministic tie-break here, order the snapshot by registration. |
| HLC overflow ceiling | Dart names its logical-counter ceiling (`_maxLogicalCounter = 0xFFFF`) and documents an "Overflow Handling" contract. kt open-codes `if (logicalCounter > 65535)` with no name and no doc. | Dart | Self-documentation only, no behavioral difference. Name and document the constant in kt (KT-E or the minor sweep). |
| Harness proof strength (four flow-backs) | (1) Dart's `runRounds(n)` + bare `hasConverged` is a delivery guarantee only under single-isolate determinism, and produced a demonstrably vacuous test — Dart's ring topology test is satisfied by four EMPTY nodes; kt's `awaitConverged` requires an explicit entry count AND id-set agreement, removing that failure class harness-wide. (2) Dart's `TestNetwork.create` passes no `onError` at all, so a Dart scenario erroring every round while still converging passes silently; every kt scenario ends on `assertNoErrors()`, with errors attributed per node (Dart can only merge every node's errors into one list). (3) Dart disposes coordinators only; kt also closes ports, unregisters them from the bus, and closes each simulated clock. (4) Dart's peer-status tests accept `anyOf(suspected, unreachable)` in four places and lean on fixed round budgets; kt pins the exact SWIM rung with a `failedProbeCount` floor and polls until the status holds. | kt, in all four | Adopt in Dart's suites — none are behavior changes, only discriminating-power gaps in the pins and the harness. All four surfaced during Batch KT-D's scenario translation. |
| Dead-loop and race pins (test idiom) | Dart asserts the compaction loop's liveness through a `compactionSchedulerForTesting.isRunning` seam; kt (no-seam ruling) proves it behaviorally by re-growing the stream so a live loop would visibly re-compact. Separately, kt stages its mid-sync race pin through the real message bus with wire encode/decode, where Dart calls the handler directly and inspects return values. | Neither on the first; kt marginally on the second | Dart's seam is simpler only because it HAS a seam kt was deliberately told not to add; kt's proof is seam-free and survives refactors of the scheduler's internals. kt's end-to-end race staging incidentally proves more of the real path — flow-back candidate if Dart's pin is ever revisited. |
| Coordinator restart and pause semantics | Dart's coordinator owns its listening subscription explicitly, cancelling and reassigning it through `startListening`/`stopListening`, AND separately gates ingestion behind `_scheduler.isRunning` in its delta-response handler — with a comment stating that a paused engine drops incoming deltas and relies on anti-entropy to re-fetch them after resume. kt has NEITHER: `Coordinator.start()` launches a collector and discards the `Job`, `stop()`/`pause()` never touch it (only `dispose()` does), and no handler in `GossipEngine`'s merge path checks a running flag. | Dart — this is a live kt defect | Two confirmed consequences, both reproduced: a "stopped" node keeps receiving and merging peer data, and each stop/start cycle stacks another live collector until duplicate collectors race the same inbound message into real duplicate-append failures. **Needs its own plan**, because the fix changes what the lifecycle methods promise: own and cancel the subscription, AND port Dart's ingestion gate. Six Dart scenarios (three restart/recovery, three pause/resume/multi-cycle) were left untranslated in Batch KT-D because they cannot pass against it; they are the acceptance suite. Its own item: [Make stopping a Kotlin coordinator actually stop it](kt-coordinator-restart-lifecycle.md). |
| New ports versus standing partitions (harness) | kt's bus had to teach `createPort` to block a newly registered port against nodes already partitioned; the bug class is structurally impossible in Dart's harness, whose partition state lives in the test network rather than the bus, so a freshly registered port there consults no partition bookkeeping at all. | Neither — it is the price kt paid for a better simulation | Not a knock on kt's block-in-place design: Dart avoids this bug only by unregistering ports to partition, which is the weaker model recorded two rows above. Fixed in Batch KT-D and pinned. |
| Where the in-memory test doubles live | Both libraries ship their in-memory message bus and time port inside the main library rather than a test-only artifact. In the Kotlin library those doubles are now substantial (a full link-condition simulator and a boundary-firing simulated clock), and a separate published testing module already exists. | Parity — deliberate on both sides, worth a joint decision | Not a unilateral move: if the doubles should live in the testing artifact, both twins should do it together, or the two shapes diverge for no reason. Raised by the final review of the scenario batch; decide once, apply to both. |
| Quiescence pacing (test-pin translation) | Dart has quiescence pacing (idle-traffic backoff) plus a test pin exercising it. kt has neither the pacing mechanism itself nor the pin — porting the pin only makes sense once the mechanism it exercises exists. | N/A — sequencing note | Not a divergence to fix directly; both the pacing port and its test-pin translation are homed in [Port the wire-efficiency behaviors to the Kotlin library](kt-port-wire-efficiency.md), which now carries this line explicitly. |
