# CC5 Batch D — Test Craft Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Raise the older test strata to the standard the post-audit files already meet — one shared coordinator builder instead of 111 hand-rolled setups, deterministic settling instead of magic pump counts, cleanup that runs on failure, assertions that can actually fail, and wire pinning that catches co-drift (CC5-5, 25–33) — plus the nine items Batches B and C routed here.

**Architecture:** Test-only batch. Production code is touched at exactly three small, named sites (the routed items below) and nowhere else. Everything else edits `test/`. The suite is its own safety net: after every task the full suite must stay green, and **no assertion may be weakened** — assertions may only be strengthened, or deleted when the task proves them vacuous (each deletion listed in the report with the proof).

**Tech Stack:** Pure Dart (`packages/gossip`), `dart test`/`analyze`/`format`, melos gates.

**Spec:** `docs/audits/2026-08-23-clean-code-audit.md` CC5-5, 25–33 + the outcome-record sections of the Batch B and Batch C plans (which route nine further items here).

## Global Constraints

- Docs say why, not how. `comment_references` live. No plan-internal shorthand in shipped docs or comments.
- Branch `cc5-batch-d` from `working-connection`; merge only with melos test+analyze green and format clean; boundary_test green.
- **Assertion discipline:** strengthening is free; deleting requires proof of vacuity in the task report (e.g. the test passes against a mutant that breaks the property it claims to pin); weakening is forbidden. Every deleted test is listed with its replacement coverage or an argument that coverage already exists elsewhere.
- **Suite count may only rise or stay level** except where a task deletes proven-vacuous tests — the report states the exact arithmetic.
- The three production-code changes are the routed items in D7; they are behavior-preserving or doc-only except where noted, and the suite is the net.
- Commit style: `test:`/`fix:`/`docs:` naming CC5 IDs; footer `Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>`.

## Design decisions (pre-filled; binding unless Joel vetoes)

- **DD1 — one builder, in `test/support/`.** `createTestCoordinator({bus, timePort, config, nodeId, onLog, onError, start})` with `addTearDown(dispose)` wired in at creation. The three existing private `createCoordinator` helpers collapse into it. Call sites needing genuinely bespoke wiring keep it and say why in a comment.
- **DD2 — settling replaces counting.** Add `pumpUntil(bool Function() condition, {int maxTurns = 64, String? describe})` to `test/support/` — a bounded condition-poll that fails with a legible message. Magic `for (var i = 0; i < N; i++) await Future.delayed(Duration.zero)` loops become `await pumpEventQueue()` ("drain what's queued") or `pumpUntil(...)` ("wait for X"). No bare counted loops survive in touched files.
- **DD3 — shorthand sweep: strip it.** Plan keys (`CD1`, `BD2`, `D1`, `M2`…) come out of shipped test comments and lib docs; the *substance* stays inline. Audit finding IDs (`CC5-n`, `COR3-n`, `WIRE4-n`, `H2`) **stay** — they resolve in `docs/audits/`, and the two engine class docs point there. This closes the question Batch C's final review left open.
- **DD4 — tautology disposition:** `expect(true, isTrue)` tests are either made real (a claim that can fail) or deleted with their claim recorded in the file's header comment.
- **DD5 — no new mocking framework.** Hand-rolled doubles in the existing style; degenerate fakes are replaced by the real in-memory implementations.
