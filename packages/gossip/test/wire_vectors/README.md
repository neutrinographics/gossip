# Wire conformance vectors

Canonical cross-library conformance vectors for the gossip wire protocol
(`docs/superpowers/specs/2026-08-28-wire-versioning.md`, §8c). **This
directory is the canonical home** (§11 decision 2): every other codebase
that speaks this wire format vendors byte-copies of these fixture files
plus a content-hash manifest, and pins a test that fails its own build if
the vendored copy's checksum ever differs from the value recorded here.
Today that's gossip-kt (`src/test/resources/wire/v1-kt/`); the app-side
translator suite in OpenDoorApp consumes plain copies of the `v1-kt` set
without the manifest machinery.

## Updating a vector

Never edit a `.frame` file or `checksums.txt` by hand, and never leave
`regenerate = true` committed. To change or add a vector:

1. Edit `wire_vectors_test.dart`'s vector definitions.
2. Set `const regenerate = true`, run
   `dart test test/wire_vectors/wire_vectors_test.dart` — it fails by
   design (`AssertionError: Wire fixtures regenerated...`).
3. Inspect every changed/added `.frame` file against spec §7.2 (v1-dart),
   §7.3 (v2), or §7.4 (v1-kt) before trusting it.
4. Set `regenerate = false`, re-run — the suite should be green.
5. Downstream consumers (gossip-kt, OpenDoorApp) re-copy the changed files
   and regenerate their own manifests in a separate, deliberate change —
   never automatically.

## Fixture format

One frame per file: `<name>.frame` holds the raw wire bytes exactly as a
peer would send/receive them (no wrapping, no encoding). Each set
directory has one `checksums.txt`: `<sha256 hex>  <filename>` per line,
sorted alphabetically by filename. A test recomputes SHA-256 over every
`.frame` file and compares it against the manifest, and separately checks
the manifest's file list is exactly the set's file list — so a fixture
added without updating the manifest (or vice versa) fails the suite.

## The four sets

- **`v1-dart/`** — §7.2, the deployed app's unprefixed dialect
  (`[type byte][JSON]`), flat per-(channel,stream) shape, JSON int-array
  payloads. Generated from and round-tripped through the real
  `SyncMessageCodec`/`MembershipMessageCodec` (`WireVersion.v1`): each
  vector is checked encode byte-exact (domain message → bytes) and
  decode→re-encode byte-exact (bytes → domain message → bytes). Includes
  the "v1+floor" emission variant (§11 decision 3):
  `deltaresponse-floor` pins that v1-send additively carries `floor` even
  though `hasMore` stays v2-only.

- **`v1-kt/`** — §7.4, the deployed server's batched dialect
  (`[type byte][JSON]`, deltas nested `channelId -> streamId -> ...`).
  **10 of the 13 files are byte-copies of gossip-kt's own committed
  goldens** (`src/test/resources/wire/v1-kt/*.frame`, last touched at
  gossip-kt commit `d20dc180e041708d1efde0f657451edbee0b3c69` on
  `feature/compaction`; copied from that branch's HEAD,
  `85f1b69b1032a4706ec3b8b21b3aa01140952d23`, at copy time) — copied
  verbatim, never regenerated by this suite, and their payload elements
  are **signed** JSON ints (e.g. `-128`, `-1`), matching the deployed
  server's actual (pre-fix) emission. **3 files are new, Dart-authored**
  frames matching this dialect's shape by hand (no Dart domain model
  understands the batched schema, so these are literal JSON, not codec
  output): `deltarequest-single` and `deltaresponse-single` wrap
  v1-dart's `deltarequest-1`/`deltaresponse-1` single-channel/stream
  scenario in the batched envelope with **unsigned** payloads (the
  upgraded emission form), and `deltaresponse-floor` pins the v1-kt
  "v1+floor" variant — `floor` structured per (channelId, streamId)
  alongside the existing nested `entries` map. This set is
  **checksum-pinned only** — no Dart codec decodes this dialect, so there
  is no encode/decode round-trip check here; gossip-kt's own vendored
  copy carries that check (W-K3/W-K4).

- **`v2/`** — §7.3, the prefixed dialect (`[0xF2][type][JSON]`). 7
  message types, types 0-5 reusing v1-dart's scenario values (`pingreq`
  in the 3-key form — no `originalRequester`, per §11 decision 4).
  `deltaresponse` exercises `hasMore: true`, a non-empty `floor`, and the
  base64 payload encoding together. Round-tripped through the real codecs
  (`WireVersion.v2`) the same way as `v1-dart`.

- **`edge/`** — negative and boundary-condition frames, hand-built (not
  routed through any encoder): unclaimed marker bytes across the whole
  `0x07`-`0xFF` range (`reserved-07`, `reserved-80`, `marker-f0`,
  `marker-f1`, `marker-f3`, `escape-ff`), a version marker with no type
  byte following it (`marker-only`), a zero-byte frame (`empty`),
  unparseable JSON after a valid type byte (`malformed-json`), and four
  frames whose *expected outcome is library-local* even though the bytes
  are shared: `v2-intlist-payload` (a legacy int-list payload inside a v2
  frame — must decode per §7.3's decoder grace), `v1-payload-signed`
  (payload `[0,-1,-128]` — must decode, normalizing to `[0,255,128]`, the
  widened §7.2 decode rule), `v1-payload-out-of-range` (payload `[300]` —
  outside `-128..255`, must be rejected), and
  `v1-deltaresponse-defaults` (no `hasMore`/`floor` keys — must decode to
  `false`/empty, not throw).

## Scenario data

Shared with gossip-kt's existing fixtures so frames read consistently
across sets: nodes `node-a`/`node-b`/`node-c`, channels `ch-1`/`ch-2`,
streams `st-1`/`st-2`, timestamps `Hlc(1_700_000_000_000 + seq, seq)`,
and the unsigned payload byte sequence `[0, 1, 127, 128, 255]` (spans the
signed/unsigned boundary this whole vector scheme cares about).

## Known divergence: explicit-zero version vector entries

Two vectors' source description (v1-kt's `deltarequest.frame`, copied
verbatim) writes a since-vector as `{"node-a": 2, "node-b": 0}` — an
explicit zero entry. Dart's `VersionVector` treats a stored zero and an
absent key as the same value (§ the value object's own normalization) and
drops explicit zeros on construction, so the **Dart-generated**
equivalents (`v1-dart/deltarequest-1.frame`, `v2/deltarequest.frame`)
encode `since` as `{"node-a": 2}` only. This is not a bug: the two forms
are the same `VersionVector` value, and the decoder produces an
equivalent object either way. It only affects byte-exactness for a
translator or codec that round-trips through a JSON representation
retaining the explicit zero — noted here so it isn't mistaken for drift
between the v1-dart and v1-kt sets.

## Byte-exactness policy

Every current vector's encode check is byte-exact: this suite fixes JSON
key order to each set's message construction order (a plain Dart `Map`
literal is insertion-ordered, matching `jsonEncode`'s emission), and no
vector so far has needed the fallback. If a future vector cannot be
byte-matched cross-language (e.g. a JSON writer whose key order or
whitespace can't be pinned to match another language's encoder), the
encode-side check for that vector may relax to "decodes back equal +
re-encodes canonically" — record the relaxation and the reason here when
it happens. No vector uses this relaxation today.
